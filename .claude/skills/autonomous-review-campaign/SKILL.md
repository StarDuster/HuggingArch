## 一句话

用户授权你自己往下推时:先把要做的事写成一份**分批的计划**(设计审先签),然后一个**自续期定时器**当发动机——每次醒来读计划和 git 历史,推进当前这批(实现→三方公审→收签→合),再设下一个定时器把自己叫醒。**两边评审都干净签了就自动合主线;拿不准的留给用户**。默认就这么一直转,不预设什么时候停。每一步的评审怎么做,看 three-party-review;本 skill 只管"没人盯着时,怎么让它自己一批批稳稳往前走、什么时候该停"。

## 默认一直跑

除非用户给了明确的停止条件,**否则默认是不停的**——一批做完接着下一批。只有三种情况才停:

1. 用户喊停;
2. 计划里的批次**真的都做完了**;
3. 剩下的全是**得问用户的事**(改对外契约、要拿主意的产品判断、纯凑指标没质量的活)。

不要自己给它安一个"跑到几点"或"跑 N 轮就收"。活没干完就继续设下一个定时器。

## 什么时候用 / 不用

- **用**:用户放权让你连续推;有一批能切分、有客观验收门(测试/计数器/oracle/golden)的改动;能接受"清楚的自动合,含糊的攒着问"。
- **不用**:就一个改动(直接用 three-party-review 走一步就行);没有客观门、全凭主观或产品决策;或有不可逆/对外副作用(发布、删数据)——这些永远先问人。

## 发动机:自续期定时器

无人值守的关键是**循环不靠你一直在线**。每个周期结尾,用定时器把下一个周期排上;定时器的 prompt 要**自包含**——因为下次醒来是一段全新的上下文,你只有 prompt 里写的东西。

```bash
cc-connect timer add --delay <N>m --desc "<项目> 驱动·<现在这步>" --prompt "$(cat <<'EOF'
<把下面这些全写进去,别指望上下文还在:
 · 主线/分支/worktree 路径 + 现在的 git 栈(哪个 commit 叠在哪个上)
 · 这个周期具体干什么(收哪份评审 / 实现哪一批)
 · 干净双签怎么办(归档评审→计划文末追处置→ff 合主线→重钉计数器);没签怎么办(照 file:line 修,fixup 压回这批的 commit,只回不签的那方)
 · 护栏(见下)
 · 后面还有哪些批、什么顺序;每批怎么走(three-party-review 里各 agent 的起法)
 · 什么时候停、怎么收官
 · 相关记忆的名字
 · 攒着的"要问用户"清单>
EOF
)"
```

- `--delay` 挑个**该回来看的时间点**:评审在跑就 15–30 分钟回看;等外部慢过程按它的节奏。别用 `-x`、别阻塞——设完定时器就交回。
- 固定节律才用 cron;一次性回看用 timer。**真要停时,记得把驱动定时器删掉**(`cc-connect timer del <id>`),否则它会一直烧。
- prompt 里有反引号、`$`、`()` 会被 shell 当命令执行——**必须**用 `<<'EOF'` 单引号 heredoc 把整段包起来。

## 计划就是"事实源"

写一份分批的计划文档(比如 proposal),每批写清:**改什么、验收门是什么、会不会动 golden**。**整份计划先让设计审签了再动手**。每合完一批,在文档末尾**追一段处置**(谁签的、必改改了啥、观察项怎么处理、和原计划的出入)。这样你任何一次醒来,读文档末尾就知道进度——不靠记忆。

## 每一批怎么走(套 three-party-review)

一个周期推一批:

1. **实现** + 自己先过一遍门(见 three-party-review 的"实现者的门":改前改后各 dump 一次、逐类定性差异、只跑相关测试、计数器涨了先解释)。
2. **起两个评审者**(一个审实现、一个审设计),无头并行,简报写成文件、prompt 只放指针(起法见 three-party-review)。
3. 设个回看定时器,**交回**——别干等。
4. 下个周期**收签**:都签且门绿 → 归档评审、计划追处置、`git -C <主线worktree> merge --ff-only <分支>`、重钉计数器、跑一下元测试;没签 → 照 file:line 修、**fixup 压回这批的 commit**、只回不签那方复审。

## 护栏:分清"能自己合"和"该问用户"

这是无人值守最要紧的一条。

- **能自动合 = 两边都干净签了**,且必改都落了。任一方没签或还有阻塞,就不合。
- **拿不准就留给用户,别硬合**:golden 数值变了、oracle 的结果、要做语义/覆盖判断(该删测试吗?该退掉一条代码路径吗?)、改了对外契约或默认——**哪怕你自己验证过是对的,也攒进"要问用户"清单**,不在没人盯着时替用户拍板。判据一句话:**"这个决定,用户有没有可能合理地不同意?" 有可能,就留给他。**
- **够不到指标就 best-effort**:能干净降的降,剩下的说明白为什么没做——别为凑数做没质量的改动或引入行为变化。
- **项目规矩优先**:commit 格式、术语、测试纪律都按仓库自己的规定;和默认习惯冲突时,项目赢。
- **不干等**:重活后台起、当轮先汇报、定时器回看;绝不阻塞在跑测试或等评审上。

## 门红了:先分清是不是你弄的

任何门一红,先判是不是本批造成的:**在干净的基线 commit 上,把同一个失败再跑一遍**。基线也红 = 早就有的债(过期的 golden、上游漂移),记进"要问用户"清单、不算你的回归、可以另开小修;基线绿、你这红 = 本批自己弄的,定位修掉。`git stash` / `git checkout <基线>` 复跑最快。连续推的过程里,经常会顺手扒出一堆主线上早就红的老债——都攒进清单。

## 怎么收官

只有前面说的三种停机条件之一成立时,才收:

1. 全量测试后台起(别 `-x`,要完整的过/挂清单);
2. 把这次的状态写进记忆(合了哪些批、指标到哪了、"要问用户"清单);
3. **删掉驱动定时器**、确认没有残留(不然它继续转);
4. 出一份**收尾报告**:做了哪些批、指标达成情况、动 golden/结构的要点、没做的项(哪些留给了用户、为什么)、**攒着的"要问用户"清单逐条**、测试状态;
5. 需要的话,只设**最后一个**定时器去收全量测试的结果,收到就彻底停。

## 常踩的坑

- 定时器 prompt 不自包含 = 下次醒来啥都不记得;把栈、下一步、记忆指针、待问清单全写进去。
- `merge --ff-only` 到一个已被别的 worktree 占着的分支会报 "already used by worktree"——去那个 worktree 里合,或专门留一个主线 worktree。
- 把必改压回某批 commit:`git commit --fixup <sha> && GIT_SEQUENCE_EDITOR=true git rebase -i --autosquash <基线>`(非交互)。
- 评审者是从它自己的 worktree 审你某个 commit 的旧 hash;你 fixup 改了 hash 不影响它审的内容,但纯文档类必改可以等它出结果再一起压。
- 收官别忘了删定时器——不删它就一直跑。
- 待问清单宁可多列:替用户做了本该他做的决定,比多问一句糟得多。
