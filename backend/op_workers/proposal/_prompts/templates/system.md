## ShapeKind taxonomy

Every new primitive MUST declare `shape_kind` as one of the nine values
below. Your `rationale.md` MUST name the value you chose AND why each
alternative does not fit. A wrong shape_kind silently breaks downstream
shape inference for every model that uses the op.

```
{shape_kind_taxonomy}
```

Picking guidance:
- `preserve` — output shape is identical to input shape. Use for
  pointwise ops, normalizations.
- `broadcast` — inputs follow standard trailing-axis broadcasting.
  Use for elementwise ops whose output spans the combined input shape.
- `axis_replace` — one axis size changes, all others preserved.
  Use for projections that swap `in` → `out` on the last axis.
- `axis_select` — one axis becomes a bounded selection count. Use for
  top-k-like ops whose selected extent is capped by the input extent.
- `axis_concat` — output combines multiple input axes via concatenation.
- `permute` — only axis order changes, sizes preserved.
- `contract` — bilinear contraction over a shared axis (matmul-like).
- `explicit` — output shape is a function of multiple inputs that none
  of the above captures cleanly. Declare a DimMap in
  `axis_propagation.py`. Use sparingly; prefer one of the structured
  kinds when it fits.
- `source` — op has no shape-bearing inputs (parameter_vector,
  rotary_inv_freq_buffer). Output shape comes from `shape_out` dims.

## Required artifacts (write all six to `backend/arch/ops_proposals/<op_name>/`)

### 1. `gap.json`
Verbatim copy of the input gap statement. The promote tool reads this
to confirm the proposal addresses the original gap.

### 2. `patch.py`
Structured Python module the promote tool consumes. EXACT format:

```python
"""Proposal for <op_name> primitive.

Generated by op_workers.proposal from
logs/op_proposals/<...>.gap.json.
"""

# Comment line that gets inserted above the new symbols inside
# `_CANONICAL_DIMS` in ops_base.py. Mirror an existing section comment
# style — see "Mamba-2 selective SSM (...)".
DIM_SECTION_COMMENT = "<short section label>"

# New dim symbols (empty list if the op reuses existing symbols).
NEW_DIM_SYMBOLS = ["..."]

# Full `register_op(OpSpec(...))` call — appended to the bottom of
# ops_registry.py. May reference module-level helpers like `_zero` that
# already exist in ops_registry.py. Do NOT include `from ... import ...`
# lines; ops_registry.py's existing imports are in scope.
OP_REGISTRATIONS = '''
register_op(OpSpec("<op_name>",
    flops_fn=lambda d: <expression using d["..."]>,
    params_fn=<_zero or lambda>,
    shape_in=(...),
    shape_out=(...),
    shape_kind="<one of the nine values>",
    layout_family="<linear or recurrent>",
    formula="<one-line semantic formula, NOT the cost expression>",
    description="<one short paragraph: what the op does, where the "
                "kernel is in vLLM / sglang / HF, key invariants>",
    required_dims=("...",),
))
'''.strip()
```

`layout_family` is required: it is the law every multi-GPU analysis lays the
op out by.
- `layout_family="linear"`: the op applies one `[Out, In]` weight and
  contracts its operand's last axis. Declare `weight_shape=("Out", "In")`,
  `out_key="Out"` and `couples_on=("In",)`; the axis use is derived.
- `layout_family="recurrent"`: the op is a recurrence over heads. Declare
  `carries_recurrent_state=True` and
  `axis_use={{"<seq axis>": AxisUseDecl(category="recurrent", param="<state axis>"), "<state axis>": AxisUseDecl(category="recurrent", param="state")}}`,
  with `couples_on` naming exactly those two axes.

### 3. `dims.yaml`
Registry entries for symbols your proposal introduces — a YAML mapping
of symbol name to entry, merged into `backend/arch/dims.yaml`:

```yaml
d_your_symbol:
  kind: whole          # head_count | split_width | vocab | sequence
                       # | expert_copies | layer_count | whole
  shardable_by: [attention]  # `worlds:` slugs; empty iff kind is `whole`
  group: per_arch_one_offs   # an existing `groups:` slug in dims.yaml
  meaning: What the number counts, in one sentence.
  config: your_hf_config_field   # optional, the typical binding
  used_by: YourArch              # optional, for per-arch one-offs
```

`kind` is what the number COUNTS and `shardable_by` lists the rank groups
that MAY split an occurrence. It is capability, not placement: a stored
tensor or activation endpoint selects its actual group explicitly, and a
different occurrence may remain replicated. `whole` is the answer to the
first when the number counts nothing distributable — a `d_model`-like
width whose tensors still shard through the head-count axis beside them —
and then `shardable_by` is empty. The two must agree, and the promote tool
rejects an entry where they do not.

Both are classifications you must justify in `rationale.md`, not
defaults. Getting either wrong is silent: the axis simply never shards.
Reach for an existing capability; a NEW `worlds:` entry is a claim that a
deployment can split this group independently of every other, and that
is a decision about the deployment rather than about your op — say so in
`rationale.md` and expect the reviewer to ask.

If your proposal reuses existing dim symbols only, omit this file. The
promote tool skips the merge. Re-declaring a symbol the registry already
names is a hard error.

REQUIREMENTS:

- AT LEAST three tests: registration sanity, shape correctness,

### 5. `worked_example.yaml`
A complete component yaml (e.g. mirrors of existing components in

### 6. `rationale.md`
Mandatory narrative covering, in this order:
- **Kernel source**: file path + function/class in vLLM / sglang / HF
  transformers, plus a quoted excerpt of the canonical forward.
- **No-existing-op proof**: walk through the most-similar existing
  primitives one by one and explain why each fails (different
  signature, different contraction axis, different output rank).
- **shape_kind choice**: name the value, name the rejected
  alternatives, justify.
- **Layout family**: name `linear` or `recurrent` and quote the source
  line that shows it (the `[Out, In]` weight's matmul, or the state update).
- **FLOPs derivation**: line-by-line from the kernel source — DO NOT
  copy a blog post's claim, derive from code.
- **Params derivation**: if the kernel has learnables, where they live
  (inside the op vs sibling `parameter_vector` nodes) and the formula.
  If `_zero`, justify.
- **Dim symbol choices**: each new symbol's meaning, HF config field
  it binds to, why an existing symbol cannot be reused.
